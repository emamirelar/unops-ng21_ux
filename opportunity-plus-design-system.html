OpportunityPlus Design System

Organization UNOPS
Year 2024–2026
Role UX Designer & Design System Lead

Context & Challenge

OpportunityPlus is UNOPS' internal platform for managing partnership opportunities, project pipelines, and organizational workflows. As the application grew in scope and complexity, the frontend accumulated inconsistent styling, duplicated component patterns, and a legacy Material-style PrimeNG preset that made visual updates fragile and time-consuming.

The challenge was to design and ship a unified design system—published as @unopsitg/ux—that would replace the fragmented approach with a single source of truth for brand theming, layout structure, and shared UI components. The system needed to serve OpportunityPlus immediately while being flexible enough for adoption by other UNOPS Angular applications.

Design System Architecture

I designed the system around three distinct layers, each addressing a different concern and allowing teams to adopt incrementally rather than all at once.

Brand Theme Layer — Three preset variants (Soft, Crisp, and Contrast) built on PrimeUIX's definePreset API, each extending a different base (Aura, Lara, Nora) while sharing a common set of UNOPS brand primitives. This lets teams choose visual tone without losing brand consistency. Semantic tokens for primary, surface, and component-level overrides (buttons, data tables, tabs, tags, cards) ensure every PrimeNG component renders on-brand without per-component CSS hacks.

Layout Shell Layer — A configurable application shell providing sidebar navigation, top bar, breadcrumbs, search, and a sticky footer. Host applications supply their menu model and optional logo overrides through injection tokens—no forking or copy-pasting layout code. The shell supports multiple menu modes (static, overlay, slim, horizontal) and adapts responsively across breakpoints.

Shared Components Layer — Purpose-built components like ux-detail-layout (a detail page shell with sticky headers, tabbed content, and a sidebar slot), ux-footer-main (a copyright bar with injectable template content), and pill-style tab navigation. Each component references design tokens exclusively—no hard-coded colors or spacing—so they respond automatically to theme changes and dark mode.

Brand Theming & Token Strategy

The UNOPS brand palette needed to map cleanly onto PrimeNG's token structure while remaining accessible across light and dark surfaces. I defined a set of brand primitives (darkblue, teal, gold, gray ramps) and wired them through semantic aliases so that changing a single primitive cascades correctly to every component that references it.

Tailwind 4 was integrated alongside PrimeNG theming, sharing the same palette through a unified @theme block. This eliminated the common problem of design-system drift where utility classes and component tokens point to different color values. Developers use standard Tailwind utilities (text-darkblue-500, bg-gray-50) and PrimeNG surfaces interchangeably, all drawing from the same source.

Dark mode is handled through a CSS class toggle (.app-dark) with the preset providing appropriate surface and text inversions. I designed the dark palette to preserve contrast ratios and visual hierarchy rather than simply inverting lightness values, paying particular attention to data-dense views like tables and dashboards.

Developer Experience & Adoption

A design system only succeeds if developers want to use it. I wrote a comprehensive adoption guide that walks teams through migration from the legacy preset to BrandSoft—covering angular.json configuration, app.config.ts wiring, menu model injection, and a phased rollout strategy so teams aren't forced into a big-bang rewrite.

The library ships with a full Storybook instance documenting every component, layout variant, and theme preset in interactive isolation. Developers can explore components, inspect token usage, and verify visual behavior before writing application code. This reduced the back-and-forth between design handoff and implementation significantly.

I also maintained a living design-system ledger—tracking which files are canonical, noting compatibility concerns around PrimeNG upgrades, and documenting boundary rules that protect the system from ad-hoc style overrides. This guardrail documentation became as important as the code itself in maintaining consistency at scale.

Layout Shell: Balancing Flexibility & Consistency

The application shell needed to feel unified across UNOPS products while allowing each team to customize navigation, branding, and page structure. I designed the shell around Angular injection tokens (MENU_MODEL, SIDEBAR_LOGO, TOPBAR_MOBILE_LOGO) so that host applications configure behavior declaratively—no subclassing, no template overrides.

The sidebar supports compact and expanded modes with smooth transitions, a footer slot for contextual actions, and horizontal menu mode for information-dense dashboards. The top bar adapts for mobile with a dedicated logo token, ensuring brand visibility on small screens without cramming the desktop layout into a responsive breakpoint.

Detail pages use ux-detail-layout, which provides a sticky header, tabbed content via a structural directive (uxDetailTab), and a right sidebar slot used for contextual features like AI-powered insights. This pattern replaced dozens of bespoke detail page layouts across the application with a single, well-tested component.

Key Deliverables

  • Published npm package (@unopsitg/ux) with brand theme presets, layout shell, and shared components for Angular 21
  • Three brand preset variants (Soft, Crisp, Contrast) with UNOPS primitives mapped to PrimeNG semantic tokens
  • Configurable application shell with injection-token-based customization for navigation, logos, and layout modes
  • Tailwind 4 integration sharing a unified @theme palette with PrimeNG design tokens
  • Interactive Storybook documentation for every component, layout variant, and theme configuration
  • Comprehensive adoption guide with phased migration strategy for the OpportunityPlus application
  • Design-system maintenance ledger and boundary rules protecting against style drift
  • Dark mode support with accessibility-validated contrast ratios across all surface combinations

Impact & Outcomes

The design system eliminated an entire category of visual bugs—inconsistent spacing, mismatched colors, and broken dark-mode surfaces—that had accumulated across the OpportunityPlus application. New features now inherit correct theming and layout behavior by default, reducing design-implementation review cycles.

Developer onboarding time for UI work dropped measurably. Instead of reverse-engineering scattered SCSS files and legacy overrides, new team members consult the Storybook, wire up the layout shell, and start building features within the design system's guardrails. The adoption guide and boundary documentation make the "right way" the easiest path.

The library's architecture—with its token-based theming and injection-token configuration—means it can serve future UNOPS Angular products beyond OpportunityPlus without forking. The Spectrum design language that began with earlier projects (PleaseAI, Data Portal) now has a production-grade Angular implementation that teams can install from npm and configure in minutes.

This project represents the full arc from design-system vision to shipped, adopted infrastructure—bridging the gap between Figma specifications and the Angular component library that developers actually import every day.
